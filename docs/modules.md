# Modules

Per-module engineering notes. Load only the section you work on.

## Reference board (`src/components/reference/`)

Infinite canvas (pan/zoom) where images, local videos and YouTube videos are laid out like a mood board. The idea and the interaction model are inspired by [AnimRef](https://github.com/lettucegoblin/AnimRef); the implementation is independent — React with native pointer events, rather than its vanilla JS and interact.js.

- **Geometry is in WORLD coordinates**, displayed through a `transform: translate()/scale()` layer. `referenceShared.ts` holds the `BoardItem` model and helpers. `ref` is the **persisted** locator (disk path, remote URL, YouTube id); `src` is the display URL **recomputed on load** by `displaySrc` — an objectURL/blob does not survive a reload.
- **Gestures are native pointer events** (`usePointerTransform.ts`), not interact.js: move, resize (8 handles, locked ratio, local frame when rotated), rotate (15° snap with Shift). During a gesture the geometry lives in **local** state coalesced in rAF, so only the manipulated item re-renders; commit to the store on `pointerup`. `BoardItem` is `memo`, so panning does not re-render items.
- **YouTube plays through a plain `<video>`, not the embedded player**: the embedded player repaints its chrome (big play button, end screen) on every seek and pause, which flashed on each loop — no `playerVars` removes it. `core/ytstream.js` resolves the stream URL with yt-dlp and relays it on `/ytstream?id=`, so the board reads it like any local video: same loop, ping-pong, trim and playhead. The relay renews the URL itself on a 403 (YouTube's URLs expire), which keeps `/ytstream?id=` a stable, persistable source. The format selector only accepts `protocol^=https` and prefers `avc1` capped at 1080p: WebView2 has no native HLS (YouTube's "Premium 1080p" itag 616 exists only as an m3u8 manifest), and a 4K VP9/AV1 stream falls back to software decoding — both end as a dead `<video>`. The same cap applies to downloads (`core/extract.js`), where a 4K AV1 file also weighs a hundred times a usable 1080p H.264. Reaching inside the iframe as AnimRef does (`contentDocument`, `--disable-site-isolation-trials`) is **not an option here**: those flags are process-wide, and `/media`+`/stream` serve arbitrary disk files relying on the browser's same-origin refusal.
- Packaged NetsuBoard provisions **`yt-dlp` as a standalone executable** (`scripts/setup.ps1`, step 3): it carries its own interpreter, so online links resolve with no Python environment. It is **mandatory** (`setupRuntimeVersion` 5): `setupStatus` counts it in `ready`, `quickSetupReady` rejects an install without it, and `setup.ps1` fails rather than skipping the download. `core/extract.js` resolves it through the same `ytDlpCommand()` as the relay, so social links (X, TikTok, Reddit, Instagram…) download their real video instead of falling back to the OpenGraph poster. **`gallery-dl` is optional**: it covers image posts (carousels, photo-only links) and is used only when the machine already provides it — a standalone `gallery-dl` next to `yt-dlp`, or a local `.venv`. Without it a photo post still lands through the OpenGraph fallback, at page-preview resolution.
- **A signed-in session, when YouTube demands one.** A growing share of videos answers `LOGIN_REQUIRED` — *"Sign in to confirm you're not a bot"* — to any caller without an account, while most videos still resolve fine. Measured against those videos in August 2026: **no** InnerTube client gets through (`tv`, `ios`, `android`, `web_safari`, `tv_simply`, `mweb`, `web_embedded`, `android_vr` and more all refuse), retrying does not help, and a [PO token](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide) is not the answer either — it unlocks *formats*, not the login wall. Only real cookies open those videos. `core/ytstream.js` therefore looks for a session **after** a refusal of that shape: a `cookiesFile` (Netscape `cookies.txt`, `nr.config.json`) first, then the browsers whose profile directory exists, Firefox leading. None is required. ⚠️ **Chrome and Edge are unreadable while they run**: they hold their cookie database with no sharing at all, so both a plain copy and a shared-read handle fail (`EBUSY`), and `--cookies-from-browser` returns *"Could not copy cookie database"* ([yt-dlp#7271](https://github.com/yt-dlp/yt-dlp/issues/7271)). Signing into YouTube once in Firefox is the only setup that keeps working without closing anything. A video that hit the wall is remembered for ten minutes: the chain costs one yt-dlp launch per candidate, and every remount used to pay all of them again.
- **YouTube fallback** = the embedded player (`YoutubeItem`), used when the relay fails (private, age-restricted, sign-in required, no yt-dlp). Exact `[in,out]` looping then needs the **IFrame Player API**, not an `end=` embed, which loops back to 0: create the player, read `getDuration`, poll and re-seek to `in` when `out` is passed. The player replaces the div, so the wrapper keeps `pointer-events:none` and `width/height:100%`. Trim changes without recreating the player (read through a ref in the poll).
- **A YouTube card takes the ratio of its video, Shorts included.** The link is all that is known when the item is posed, so a `/shorts/` URL poses 9:16 and anything else 16:9. That is a hint, not the answer — a vertical video is just as often shared as a plain `watch?v=` link. The relayed stream is where the true ratio first appears (`videoWidth`/`videoHeight` on `loadedmetadata`), and the card is reshaped there around its own centre at constant area, which also repairs boards posed before the measurement existed. A proxy never feeds the measurement (its dimensions are the excerpt's), a cropped item is left alone (its box deliberately differs from the source), and the patch is not recorded in history — a measurement is not a user edit.
- Generic HTML pages exposing OpenGraph media or HTML5 `<video>`/`<source>` can stay linked or be downloaded according to the Board preference. They remain generic pages and do not become named settings providers.
- **Local videos**: `<video>` in WebView2 does not read `.mkv`. Route mp4/mov/webm to `/media` (Range, seek and loop work), everything else to `/stream` (remux, copy when the codec is native).
- **A local cut is played as a PROXY, not the raw file**: a cut (`trimOut` set) of a local file — often `.mkv`/HEVC — showed the **start of the file** because mid-file seeking fails over a stream copy, which reads as "wrong media". Such items play an mp4 proxy of the exact range (whole loop, no seek), regenerated on each mount (server cache), so nothing temporary is persisted.
- **Persistence** = `core/reference.js`: multiple scenes plus assets (pasted images written to disk, name = content hash). **SQLite via `node:sqlite`** when available, **JSON-file fallback** otherwise, same public API. Prepared statements are created **per call**: a retained `StatementSync` can be finalised by the GC, producing "statement has been finalized" on save.
- **Detachable window**: a second Tauri `WebviewWindow` (label `reference`, frameless, always-on-top) on the **same renderer** at hash `#reference`; `App.tsx` detects it and renders the board bare. Hand-off to that window goes through a reserved scene; `reference:push` pushes live additions. The detached window has **no toolbar and no icons** (requirement) — only a thin drag strip; every action is in the context menu. **In-place pinning**: when the main window is pinned, `ReferencePanel` renders the board bare in the same way, giving a floating board without opening a second window.
- **Autosave** is debounced into a reserved scene and restored at startup. It also silently rewrites a **named** scene. `save()` and `saveAuto()` both surface errors as a notice, with a single notice until the next success so a debounced burst does not spam. Notice auto-clearing is **centralised** in `setNotice` (error 5s, ok 2.6s, `sticky` for progress notices) — callers own no timers.
- **Text notes** (kind `text`): sticky notes, double-click to edit, **committed live on change** so text is never lost regardless of how editing ends. Default font is handwritten (Caveat, bundled). While editing inline, the inspector **stays visible** (style bar reachable mid-typing, PureRef-style): the textarea's `onBlur` only exits editing if focus does not move into that bar. For other item types the inspector hides during editing.
- **Frames** (kind `frame`) are containers: a discreet section panel with the title label as a tab **above** the top edge (the frame wrapper is `overflow-visible`, the others are `overflow-hidden`). Fill has 3 modes: none / tint / solid. A frame sits **at the back** (`z=0`, never brought to front on click) and **moving it moves the items it contains** (centre-in-rect test at commit).
- **Drawing is hand-made** (`DrawLayer.tsx`, kind `draw` = board-wide singleton, zero third-party dependency — Excalidraw was dropped for bugs and branding). Tools: select, pen, highlighter, line, arrow, rectangle, ellipse, diamond, eraser, plus colour, width, opacity steps, undo/redo. Shift constrains (15° angles, regular shapes). Shapes are stored in **world coordinates** and rendered in an `<svg>` transformed like the board layer, so ink scales with zoom; stroke width is stored in world units. Arrowheads are configurable at both ends; connector routing is straight / curved (quadratic control point) / elbowed. Hit-testing: bbox interior for closed shapes, proximity for pen and lines.
- **Board performance — five levers, all measured**:
  1. Static shapes and their hit targets are `memo` sub-components keyed on `shapes` **alone** (not on the view), so N shapes are not reconciled per frame.
  2. The pan/zoom `transform` lives on a wrapper `<div>` (`will-change:transform`), **not** on the `<svg>`: a div is reliably promoted to a composite layer, while a transformed `<svg>` is not always promoted in Chromium and re-rasterised on pan — that was the perceived lag.
  3. **Imperative panning**: during the gesture there is **no** `setView` per pointermove (a 1000 Hz mouse would re-render the whole board per event). The view lives in a ref, applied in a coalesced rAF to the `[data-board-pan]` layers, with a single `setView` commit on `pointerup`. The dot grid is a dedicated div translated **modulo the step** (GPU composite, zero repaint; the old `backgroundPosition` re-rasterised the viewport every frame). Wheel zoom is coalesced to one per frame.
  4. **Spatial culling** (`useBoardCulling.ts`): past 40 items, only those whose bbox intersects the viewport enlarged by 75% are **mounted** (a board carries hundreds of media = as many decoders and layers). The zone is recomputed only when the viewport leaves it, never per pan frame; the selected or edited item is always mounted. A re-render during a gesture would restore the **stale** transform from the store, so a `useLayoutEffect` re-applies the live view before paint.
  5. **Fewer re-renders**: zoom is no longer a prop of items (read once at gesture start), content bounds are computed only when the placement frame is active, and image sequences preload a 24-frame window instead of the whole sequence.
- **Media picker** ("From the project") is a **right-docked panel with a transparent, unblurred overlay** and `modal={false}`, so the board stays sharp behind it. It accepts OS file drops, and its cards reuse the derush card mechanics (lazy thumbnail, hover preview, `content-visibility`) so they look and behave identically. Two modes: Browse (rush list → cuts of that rush, with on-demand detection if nothing is cached) and AI search (text query → nearest shots, thumbnails from the **shared** cache). Cards are draggable onto the board with a typed payload; the drop converts the cursor into board coordinates. **Thumbnails are lazy** (IntersectionObserver, `rootMargin:300px`): a rush with 1400 shots no longer floods ffmpeg.
- **Multi-selection**: marquee (left drag on the background; pan is middle-click or Space+drag). With ≥2 items selected the inspector becomes an arrange bar (align, distribute, grid).
- **Cropping** uses a normalised `crop` on the item, displayed via an oversized media element plus translate; confirming adjusts the item ratio so nothing distorts. Images and videos both.
- **Shortcuts** (`useBoardShortcuts`): **all command shortcuts are rebindable**, combos included, through `prefs.shortcutKeys`; the handler matches a combo string to an action then dispatches. Drawing tool keys are rebindable too. Not rebindable ("Gestures"): arrows (nudge, step ÷ scale so pixels stay constant on screen, Shift ×10, burst coalesced into one undo), paste (browser event), pan, wheel, marquee, Shift constraints.
- **Board settings** is a non-modal floating panel with 4 tabs (Appearance / Media / Behaviour / Shortcuts) — a flat list of 13 sections was interminable. It is reachable from the home screen, the toolbar **and the context menu**, the last being the only route in pinned or detached mode. Preferences persist in `localStorage` and are shared by all scenes.
- **Right-click covers everything** (`BoardMenu.tsx`): `onContextMenuCapture` targets what is under the cursor **before** the menu opens, so the menu is adaptive — item actions when an item is aimed at, shape actions when a drawn shape is, then always the board actions. Aiming inside an existing multi-selection **keeps** it (that is where the group actions live); empty space clears it. Right-click never starts a gesture: move, resize, rotate, marquee, pan, drawing and the crop box are all left-button only.
- **The right-click policy is app-wide** (`components/common/TextContextMenu.tsx`, mounted once per window in `App.tsx`): the WebView2 native menu is suppressed everywhere, and text fields — board notes, dialogs, settings — get an in-app Cut / Copy / Paste / Select all menu instead; a plain text selection outside a field gets Copy. Its listener runs in the **capture** phase, so a field being edited on the board opens the edit menu, not the board menu; surfaces carrying their own `<ContextMenu>` (board, home cards, error badge) are left alone. Inside a dialog the menu is portalled **into** the dialog content, otherwise its clicks would read as an outside press. The home screen, which has no toolbar, carries its own menu (new project, open project, storage folder, settings).
- **Tooltips**: every icon button goes through the custom `Tooltip` wrapper; native `title=` is never used. Colour pickers are wrapped in a `TooltipTrigger render={<span/>}` so the picker's own popover trigger stays inside.
- Media elements are `display:block` (`<video>`, `<img>`, YouTube iframe) to avoid the thin horizontal line from inline baseline gaps during playback.

## `.netsu` container

`core/netsu/`, façade `core/netsu.js`. The share and project format is a **SQLite container**, no longer a ZIP.

- A file written in one shot cannot be the source of edits. Here items are **one row each** (`board_items`) and media bytes are **content-addressed and chunked** (`blobs`/`blob_chunks`, 8 MiB) — `node:sqlite` exposes no incremental blob API, so a multi-gigabyte medium never passes through memory whole.
- `db.js`: `page_size=8192` **before** the first write, WAL, `synchronous=NORMAL`, `rev` incremented per transaction, `seal(dest)` = checkpoint + `VACUUM INTO` (**never** `VACUUM` on the open database). Export writes a `.part` **inside the target folder** then renames (atomic on the same volume), so a half-written `.netsu` never exists.
- **The type is decided by the first bytes** (`sniff`: `SQLite format 3\0` vs `PK\x03\x04`), not by the extension: v1 ZIP archives already sent out stay importable (read-only legacy path).
- **"Save as" makes the `.netsu` the WORKING DOCUMENT** (`core/netsu/{session,project,sidecar,recents}.js`, tested). Sharing and saving are different operations and do not share code: sharing builds a **self-contained** file in one shot with re-encoded media; a project rewrites the **same** file a hundred times. Four rules:
  1. **The file stays OPEN** (session registry keyed on the resolved lowercase path — two spellings of the same file on Windows would open two databases on one file). Two caches live there for the same reason: content identity per path (otherwise every save re-reads the first megabytes of every rush) and last JSON written per item.
  2. **Incremental writes, compared on the item's JSON**: a thousand-item board with one moved item writes one `UPDATE`, and a save with no change writes **zero** rows (locked by test). That is the reason for the row-per-item schema.
  3. **No re-encoding**: a project only **references** rushes. The share path re-encodes per medium, which would mean tens of seconds per save.
  4. **Companion folder `my-project.medias/`**: whatever has no home of its own on disk (a pasted image, a medium fetched from a link) used to live in the **global** asset store shared by every board, so a project saved elsewhere left its media behind and clearing the store broke unrelated projects. The token path is **relative** to the `.netsu`, the only form that survives a move, and the pair moves together. The folder is **browsable**, so it is sorted: `images/`, `videos/`, one folder per image sequence under `sequences/`, `other/` as a fallback, and each file is named after its board item with a 12-hex content suffix (`aurora-2f4a70a71de8.jpg`) — that suffix is what keeps deduplication free. A save **never moves an already-sorted medium**, even when its item was renamed: a Ctrl+S must not churn the folder. A project written in the older flat layout is sorted on its next save by **renaming**, never by copying bytes. A media adopted from another project's companion folder (that is, "Save as") moves into the new one, so the copy does not stay tied to the original. A `..` in a received token cannot escape the folder, and orphan cleanup — which also prunes emptied sequence folders — is **suspended when a save empties the document at once** — that is almost always a board that has not loaded yet, and bytes do not come back.
- **Nothing a save deletes can still be needed.** Cleanup is the only step that destroys bytes, so three things feed its keep list. The **media held before an upscale** (`prevMedia`) is tokenised and adopted like any other project medium — otherwise the "undo upscale" button pointed at a file the same save had just erased. The board sends `retain`, the durable locators its **undo history** still holds: autosave fires 500 ms after a deletion, and without that list Ctrl+Z brought the item back without its pixels. Finally **saves are serialised per file** (`queued` in `core/netsu.js`): a save that copies a rush outlives the next autosave tick, and two concurrent passes would let the older one's cleanup erase what the newer just adopted.
- **A project does not pay twice for the same medium.** Blobs are cleaned like companion files: bytes no room references leave, and `PRAGMA auto_vacuum = INCREMENTAL` (set at creation) returns the freed pages. Opening a shared file as a project copies its media into the companion folder, so keeping the embedded originals would double the file for good. Copying and hashing large media run **asynchronously**, one chunk per transaction (`putFileAsync`, `adoptAsync`): the core is single-threaded, and a synchronous multi-gigabyte copy froze previews, the media server and every other module for the duration. Sharing reports its progress item by item over `netsu:progress`.
- **A shared file describes media, never machines.** Export writes `media.path` empty: an absolute path means nothing on the recipient's disk and publishes the sender's session name and disk layout, while relocation works on name + size + head fingerprint. `prevMedia` is reduced to its **origin link** if it has one and dropped otherwise — its bytes live with the sender, embedding them would double the weight for a version nobody looks at. Missing media relocate **in bulk** (`netsu:relocateFrom`): one folder, every medium recognised by name and size, and homonyms of equal size are never guessed.
- A board bound to a file **leaves** the internal library (`sceneId: null`): two copies of one board would diverge. After "Save as" succeeds, the file recent records the converted internal scene id, then removes that scene; the id remains a de-duplication guard if cleanup must be retried. NetsuBoard renders session, file projects, and unconverted scenes in one **Recent** grid. The recents registry otherwise stores file addresses, filters missing files **on read** and never rewrites, so a project on an unplugged drive is not forgotten forever. A v1 ZIP archive opens **read-only** rather than being refused; "Save as" converts it.
- **The global asset store is swept at boot** (`refStore.sweepAssets`, `NR_HOME/reference/assets`). It receives everything the app makes for a board — pasted images, fetched media, extracted frames, **upscale outputs**, hundreds of megabytes per shot — and nothing ever left it. A file goes only if no library scene references it (item refs, sequence frames, `prevMedia`, `localMedia`) **and** it is older than the 14-day grace period. It runs at startup and only there, because a board opened from a `.netsu` still points at that store in memory. Board upscales also go through `core/upscaleLedger.js` now: same source, same bounds, same settings returns the file already produced instead of paying for the GPU again.
- **Media embed levels** (`core/netsu/levels.js`, pure, tested): `link` (poster only) · **`preview` (default, the played range re-encoded)** · `margin` (widened range so bounds stay adjustable without the original) · `full`. Quality and margin are settings. **Do not produce embedded media through `proxySegment`**: it caps duration at 4s for looping previews — `core/netsu/embed.js` reuses the encoding building blocks without that cap or the playback queue. `netsu:weigh` estimates the weight of all four levels without encoding anything. An abnormally long range is **reported, never silently trimmed**.
- **The notebook is a `.netsu` document too** (`core/netsu/notebookDoc.js` + a router in `core/notebook.js`, tested). SQLite was chosen for the **access pattern**, not the file size: the notebook saves **as you type** (700 ms debounce) and one keystroke touches **one** page, whereas the ZIP re-serialised the whole page index and recompressed it at every pause, and had to be fully decompressed to open a single page or search a word. `sqliteBackend` takes a **handle** instead of a path, so the same tables and queries live either in `NR_HOME` or in a container. `createNotebookStore` became a **router**: channels do not all carry the target notebook, so routing uses the most precise id available and otherwise asks each store which one owns the object — a primary-key `SELECT`, never a scan. Files come **before** `NR_HOME`: after "Save as", the file is the truth. Three points hold: the notebook **keeps its id** when moving (otherwise its pages, mentions and subpages point at a vanished notebook), the trash follows, and the original copy is removed from `NR_HOME` only **after** verifying the number of pages written (a full disk must not leave the user with no notebook at all). Media go to the companion folder — **flat, at its root**, since a notebook token carries a file name and no path — and their URLs are stored as **tokens** (`core/netsu/mediaTokens.js`): a block URL carries an absolute path and a port, neither of which survives moving the project or restarting the core on another port. The renderer supplies its URL template on open — only it knows its base and token.



> The notebook document type is part of the `.netsu` router, but **the notebook itself is not a NetsuBoard surface**: `src/components/notebook/` is inherited from NetsuRush and nothing in `App.tsx` reaches it.

## Turbo upscale on a board item (`boardUpscale.ts` + `UpscaleItemDialog.tsx`)

Upscaling an item is a board action, not a module: pick a shader and a factor, the core runs one ffmpeg `libplacebo` job, and the result replaces the item's media. The engine rules — shader ids, ArtCNN suffixes, the `master`-build ban — are invariants and live in [`invariants.md`](invariants.md#turbo-upscaling--shaders-only).

- `useBoardUpChoices.ts` narrows the shader list to what the machine can actually run; a GPU without a working Vulkan/`libplacebo` path offers nothing rather than failing mid-job.
- Three shapes, one engine: still image → PNG, **animated GIF → GIF** (`runShaderGif`, all frames), video → HEVC mp4. The core picks by extension, so a Giphy item upscales like any other picture.
- In dev the shaders live in `vendor/shaders` (gitignored, `scripts/fetch-shaders.ps1`). Without them **every** job fails, video included — the directory is also the ffmpeg working directory.
- **A still frame is read without `-ss`.** An input seek to 0 on the image2 demuxer eats the only frame: ffmpeg writes nothing and still exits 0, so the board ended up pointing at a file that was never created. `writeFrame` also refuses an empty output rather than reporting success.
- **`libplacebo` drops alpha** whatever `format=` asks for. A transparent source is split (`alphaGraph`): colour through the shader, alpha scaled beside it with lanczos, `alphamerge` at the end — and for a GIF, a reserved palette entry (`reserve_transparent`, `alpha_threshold`).
- There is **no AI engine and no fallback to one**. `core/upscaleArgs.js`, `core/upscaleLedger.js` and the `netsulab-*` tests still describe NetsuRush's Python upscaler; they are inherited, not a second engine to reach for.
