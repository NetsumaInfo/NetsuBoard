# Modules

Per-module engineering notes. Load only the section you work on.

## Reference board (`src/components/reference/`)

Infinite canvas (pan/zoom) where images, local videos and YouTube videos are laid out like a mood board. The idea and the interaction model are inspired by [AnimRef](https://github.com/lettucegoblin/AnimRef); the implementation is independent — React with native pointer events, rather than its vanilla JS and interact.js.

- **Geometry is in WORLD coordinates**, displayed through a `transform: translate()/scale()` layer. `referenceShared.ts` holds the `BoardItem` model and helpers. `ref` is the **persisted** locator (disk path, remote URL, YouTube id); `src` is the display URL **recomputed on load** by `displaySrc` — an objectURL/blob does not survive a reload.
- **Gestures are native pointer events** (`usePointerTransform.ts`), not interact.js: move, resize (8 handles, locked ratio, local frame when rotated), rotate (15° snap with Shift). During a gesture the geometry lives in **local** state coalesced in rAF, so only the manipulated item re-renders; commit to the store on `pointerup`. `BoardItem` is `memo`, so panning does not re-render items.
- **A still local image is drawn from a pyramid** (`boardImageLod.ts`, `core/thumbs.js` `imageTiers`): the core writes WebP copies at long sides 512, 1024 and 2048 in **one ffmpeg pass** (only the sides at least 1.5x below the source), cached in the thumbnail directory. The item shows the smallest level sharper than its long side in **device pixels** at the octave-quantised zoom (crop included), and the source only beyond 2048; a sharper level already shown is kept while it is one step above the need. A source above 6 MP, or not measured yet, stays a placeholder until its levels arrive instead of decoding in full. A level is only shown once decoded off-screen. Scenes prime every level in one `imageTiersResolve` call.
- **YouTube plays through a plain `<video>`, not the embedded player**: the embedded player repaints its chrome (big play button, end screen) on every seek and pause, which flashed on each loop — no `playerVars` removes it. `core/ytstream.js` resolves the stream URL with yt-dlp and relays it on `/ytstream?id=`, so the board reads it like any local video: same loop, trim and playhead. Ping-pong feeds the relay URL to ffmpeg, which encodes the range forwards then backwards into one looping file (`docs/invariants.md`). The relay renews the URL itself on a 403 (YouTube's URLs expire), which keeps `/ytstream?id=` a stable, persistable source. The format selector only accepts `protocol^=https` and prefers `avc1` capped at 1080p: WebView2 has no native HLS (YouTube's "Premium 1080p" itag 616 exists only as an m3u8 manifest), and a 4K VP9/AV1 stream falls back to software decoding — both end as a dead `<video>`. The same cap applies to downloads (`core/extract.js`), where a 4K AV1 file also weighs a hundred times a usable 1080p H.264. Reaching inside the iframe as AnimRef does (`contentDocument`, `--disable-site-isolation-trials`) is **not an option here**: those flags are process-wide, and `/media`+`/stream` serve arbitrary disk files relying on the browser's same-origin refusal.
- Packaged NetsuBoard provisions **`yt-dlp` as a standalone executable** (`scripts/setup.ps1`, step 3): it carries its own interpreter, so online links resolve with no Python environment. It is **mandatory** (`setupRuntimeVersion` 5): `setupStatus` counts it in `ready`, `quickSetupReady` rejects an install without it, and `setup.ps1` fails rather than skipping the download. `core/extract.js` resolves it through the same `ytDlpCommand()` as the relay, so social links (X, TikTok, Reddit, Instagram…) download their real media instead of falling back to the OpenGraph poster. **`gallery-dl` is optional** and is only reached when the machine already provides one (standalone next to `yt-dlp`, or a local `.venv`); nothing depends on it.
- **A post is a LIST OF SLIDES, not one medium.** `core/extract.js` enumerates them in one metadata pass (`-J -i --ignore-no-formats-error` — without that flag a single photo slide makes yt-dlp exit non-zero and the whole post is discarded), downloads the slides carrying a stream, and takes the others from their largest thumbnail, which is the full-resolution file. A slide whose stream fails keeps its thumbnail.
- **A share link that names a slide posts only that slide** (`slideIndex` in `embeds.ts` reads `img_index`, `/photo/N`, passed as `index` to `extractMedia`); a bare link lands the whole post, in a row in reading order. **X/Twitter has its own resolver**: its yt-dlp extractor exposes neither format nor thumbnail for a photo tweet, so media come from the syndication endpoint of the official embeds (`cdn.syndication.twimg.com/tweet-result`), photos at `name=orig`. `OG_POSTER_ONLY_PROVIDERS` lists the providers whose OpenGraph is only a poster: a failed extraction falls back to the embed card, never to that thumbnail.
- **A signed-in session, when YouTube demands one.** A growing share of videos answers `LOGIN_REQUIRED` — *"Sign in to confirm you're not a bot"* — to any caller without an account, while most videos still resolve fine. Measured against those videos in August 2026: **no** InnerTube client gets through (`tv`, `ios`, `android`, `web_safari`, `tv_simply`, `mweb`, `web_embedded`, `android_vr` and more all refuse), retrying does not help, and a [PO token](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide) is not the answer either — it unlocks *formats*, not the login wall. Only real cookies open those videos. `core/ytstream.js` therefore looks for a session **after** a refusal of that shape: a `cookiesFile` (Netscape `cookies.txt`, `nr.config.json`) first, then the browsers whose profile directory exists, Firefox leading. None is required. ⚠️ **Chrome and Edge are unreadable while they run**: they hold their cookie database with no sharing at all, so both a plain copy and a shared-read handle fail (`EBUSY`), and `--cookies-from-browser` returns *"Could not copy cookie database"* ([yt-dlp#7271](https://github.com/yt-dlp/yt-dlp/issues/7271)). Signing into YouTube once in Firefox is the only setup that keeps working without closing anything. A video that hit the wall is remembered for ten minutes: the chain costs one yt-dlp launch per candidate, and every remount used to pay all of them again.
- **YouTube fallback** = the embedded player (`YoutubeItem`), used when the relay fails (private, age-restricted, sign-in required, no yt-dlp). Exact `[in,out]` looping then needs the **IFrame Player API**, not an `end=` embed, which loops back to 0: create the player, read `getDuration`, poll and re-seek to `in` when `out` is passed. The player replaces the div, so the wrapper keeps `pointer-events:none` and `width/height:100%`. Trim changes without recreating the player (read through a ref in the poll).
- **A YouTube card takes the ratio of its video, Shorts included.** The link is all that is known when the item is posed, so a `/shorts/` URL poses 9:16 and anything else 16:9. That is a hint, not the answer — a vertical video is just as often shared as a plain `watch?v=` link. The relayed stream is where the true ratio first appears (`videoWidth`/`videoHeight` on `loadedmetadata`), and the card is reshaped there around its own centre at constant area, which also repairs boards posed before the measurement existed. A proxy never feeds the measurement (its dimensions are the excerpt's), a cropped item is left alone (its box deliberately differs from the source), and the patch is not recorded in history — a measurement is not a user edit.
- Generic HTML pages exposing OpenGraph media or HTML5 `<video>`/`<source>` can stay linked or be downloaded according to the Board preference. They remain generic pages and do not become named settings providers.
- **Local videos**: `<video>` in WebView2 does not read `.mkv`. Route mp4/mov/webm to `/media` (Range, seek and loop work), everything else to `/stream` (remux, copy when the codec is native).
- **A local cut is played as a PROXY, not the raw file**: a cut (`trimOut` set) of a local file — often `.mkv`/HEVC — showed the **start of the file** because mid-file seeking fails over a stream copy, which reads as "wrong media". Such items play an mp4 proxy of the exact range (whole loop, no seek), regenerated on each mount (server cache), so nothing temporary is persisted.
- **Persistence** = `core/reference.js`: multiple scenes plus assets (pasted images written to disk, name = content hash). **SQLite via `node:sqlite`** when available, **JSON-file fallback** otherwise, same public API. Prepared statements are created **per call**: a retained `StatementSync` can be finalised by the GC, producing "statement has been finalized" on save.
- **Detachable window**: a second Tauri `WebviewWindow` (label `reference`, frameless, always-on-top) on the **same renderer** at hash `#reference`; `App.tsx` detects it and renders the board bare. Hand-off to that window goes through a reserved scene; `reference:push` pushes live additions. The detached window has **no toolbar and no icons** (requirement) — only a thin drag strip; every action is in the context menu. **In-place pinning**: when the main window is pinned, `ReferencePanel` renders the board bare in the same way, giving a floating board without opening a second window.
- **Autosave** is debounced into a reserved scene and restored at startup. It also silently rewrites a **named** scene. `save()` and `saveAuto()` both surface errors as a notice, with a single notice until the next success so a debounced burst does not spam. Notice auto-clearing is **centralised** in `setNotice` (error 5s, ok 2.6s, `sticky` for progress notices) — callers own no timers.
- **Text notes** (kind `text`): sticky notes, double-click to edit, **committed live on change** so text is never lost regardless of how editing ends. Default font is handwritten (Caveat, bundled). While editing inline, the inspector **stays visible** (style bar reachable mid-typing, PureRef-style): the textarea's `onBlur` only exits editing if focus does not move into that bar. For other item types the inspector hides during editing.
- **Frames** (kind `frame`) are containers: a discreet section panel with the title label as a tab **above** the top edge (the frame wrapper is `overflow-visible`, the others are `overflow-hidden`). Fill has 3 modes: none / tint / solid. A frame sits **at the back** (`z=0`, never brought to front on click) and **moving it moves the items it contains** (centre-in-rect test at commit).
- **Drawing is hand-made** (`DrawLayer.tsx`, kind `draw` = board-wide singleton, zero third-party dependency — Excalidraw was dropped for bugs and branding). Tools: select, pen, highlighter, line, arrow, rectangle, ellipse, diamond, eraser, plus colour, width, opacity steps, undo/redo. Shift constrains (15° angles, regular shapes). Shapes are stored in **world coordinates** and rendered in an `<svg>` transformed like the board layer, so ink scales with zoom; stroke width is stored in world units. Arrowheads are configurable at both ends; connector routing is straight / curved (quadratic control point) / elbowed. Hit-testing: bbox interior for closed shapes, proximity for pen and lines.
- **A pen stroke carries its own width, point by point** (`DrawShape.pw`, one factor per point, optional). Pressure — widened by tilt when that setting is on — is **baked in as the stroke is drawn**: changing a preference later never redraws existing ink. A variable width cannot be a `stroke-width`, which is one constant per path, so such a stroke renders as a **filled outline** (`penOutline`, ±radius along the local normal, round caps as arcs) in the three places ink is painted: the SVG layer, the canvas export and the SVG export. Hardware with no sensor reports a flat `0.5` (spec value), and a stroke where nothing ever varies drops `pw` entirely and stays a constant-width path — what a mouse draws. `pointermove` is read through `getCoalescedEvents()`: a stylus emits at 200–1000 Hz and the browser delivers one event per frame with the rest stacked inside it. The **eraser end** of a stylus (`button` 5 / `buttons` bit 32) erases whatever tool is selected.
- **Board performance — five levers, all measured**:
  1. Static shapes and their hit targets are `memo` sub-components keyed on `shapes` **alone** (not on the view), so N shapes are not reconciled per frame.
  2. The pan/zoom `transform` lives on a wrapper `<div>` (`will-change:transform`), **not** on the `<svg>`: a div is reliably promoted to a composite layer, while a transformed `<svg>` is not always promoted in Chromium and re-rasterised on pan — that was the perceived lag.
  3. **Imperative panning**: during the gesture there is **no** `setView` per pointermove (a 1000 Hz mouse would re-render the whole board per event). The view lives in a ref, applied in a coalesced rAF to the `[data-board-pan]` layers, with a single `setView` commit on `pointerup`. The dot grid is a dedicated div translated **modulo the step** (GPU composite, zero repaint; the old `backgroundPosition` re-rasterised the viewport every frame). Wheel zoom is coalesced to one per frame.
  4. **Spatial culling** (`useBoardCulling.ts`): past 40 items, only those whose bbox intersects the viewport enlarged by 75% are **mounted** (a board carries hundreds of media = as many decoders and layers). The zone is recomputed only when the viewport leaves it, never per pan frame; the selected or edited item is always mounted. A re-render during a gesture would restore the **stale** transform from the store, so a `useLayoutEffect` re-applies the live view before paint.
  5. **Fewer re-renders**: zoom is no longer a prop of items (read once at gesture start), content bounds are computed only when the placement frame is active, and image sequences preload a 24-frame window instead of the whole sequence.
- **Media picker** ("From the project") is a **right-docked panel with a transparent, unblurred overlay** and `modal={false}`, so the board stays sharp behind it. It accepts OS file drops, and its cards reuse the derush card mechanics (lazy thumbnail, hover preview, `content-visibility`) so they look and behave identically. Two modes: Browse (rush list → cuts of that rush, with on-demand detection if nothing is cached) and AI search (text query → nearest shots, thumbnails from the **shared** cache). Cards are draggable onto the board with a typed payload; the drop converts the cursor into board coordinates. **Thumbnails are lazy** (IntersectionObserver, `rootMargin:300px`): a rush with 1400 shots no longer floods ffmpeg.
- **Multi-selection**: marquee (left drag on the background; pan is middle-click or Space+drag). With ≥2 items selected the inspector becomes an arrange bar (align, distribute, grid).
- **Pen tablets and touch screens are first-class** (`tabletInput.ts` + the Pen settings tab). Three machines want different things and the `auto` settings resolve them against a live probe (`matchMedia` + `maxTouchPoints` + whether a stylus has been seen): a display tablet next to a mouse, a tablet with no screen, and a touch-first machine with no wheel, no keyboard and no hover. **Two contacts pinch** — the gap sets the scale, the midpoint sets the translation, both relative to the frame captured at the second contact, so the gesture does not drift. Contacts are tracked in the **capture** phase on the board container: an item stops propagation to claim its own gesture, and a second finger lands on an item far more often than on the background. A pinch never steals a gesture already owned by an item (`navigating` held with no board gesture) and cancels a stroke in progress instead of drawing a second one. **Palm rejection** drops touch contacts while a stylus has been in play in the last 900 ms — the OS does it where the digitiser can, and the spec gives a page no way to opt out of or into that, so this is the net underneath. The **barrel button** can navigate instead of opening the context menu. Hover-revealed controls are the other half: Tailwind v4 wraps `hover:` in `@media (hover: hover)`, so on a pointer that never hovers such a control **does not exist**; the `hoverless:` variant (`src/index.css`) is that media query's other branch, and the Pen tab can force it on a machine that does hover.
- **Cropping** uses a normalised `crop` on the item, displayed via an oversized media element plus translate; confirming adjusts the item ratio so nothing distorts. Images and videos both.
- **Shortcuts** (`useBoardShortcuts`): **all command shortcuts are rebindable**, combos included, through `prefs.shortcutKeys`, and any of them can be **unbound** (Delete while capturing, kept as an empty string through `mergeKeys`). **One frame step serves both kinds of playback** (`boardFrameStep.ts`): on a film strip it moves the frame index, on a video or relayed YouTube player it pauses the item (`playMode: "off"`) and seeks by exactly 1/fps — the cadence comes from ffprobe through `reference:playInfo` (23.976, not 24; HTML5 exposes none) and is cached per source, with a 25 fps fallback for a remote link that cannot be probed. The handler is the single dispatcher: the handler matches a combo string to an action then dispatches. Drawing tool keys are rebindable too. Not rebindable ("Gestures"): arrows (nudge, step ÷ scale so pixels stay constant on screen, Shift ×10, burst coalesced into one undo), paste (browser event), pan, wheel, marquee, Shift constraints.
- **Both toolbars are arranged by the user** (`toolbarButtons.tsx`): the full bar (`prefs.barButtons` / `barButtonsEnd`, around the project name) and the pinned one, which also picks its edge (`prefs.pinnedSide`, left/right turning it vertical). Rendering order is the LIST's, never the preference's — a bar that reshuffles has to be relearned. It is arranged by **dragging onto a mock of the bar itself** (`PinnedBarEditor.tsx`): a bank of unplaced icons, two drop zones for the two ENDS (the useful room on a pinned bar is at both extremities), same orientation as the chosen edge. Rendering order is the preference's, zone by zone — that is what a drag-and-drop means. Plain HTML5 DnD, no library, and clicking stays a complete path (add from the bank, click a placed icon to remove) since a setting only reachable by drag is a setting lost. Pin, detach and attach are absent from the bank — they are the way out of the pinned format — and always sit last. Two actions that only had a shortcut are offered there too, extract palette and tidy.
- **Board settings** is a non-modal floating panel with 5 tabs (Appearance / Media / Behaviour / Pen / Shortcuts) — a flat list of sections was interminable. The Pen tab ends on a **live hardware read-out**: hovering a stylus over the window fills in pressure and tilt without drawing, which is the only way to tell a disabled setting from a driver that exposes no sensor (Wacom with Windows Ink off reports a flat `0.5`). Its shortcut editor resolves labels in the namespace the caller names (`ns`), since a `labelKey` is relative to its own module. It is reachable from the home screen, the toolbar **and the context menu**, the last being the only route in pinned or detached mode. Preferences persist in `localStorage` and are shared by all scenes.
- **Right-click covers everything** (`BoardMenu.tsx`): `onContextMenuCapture` targets what is under the cursor **before** the menu opens, so the menu is adaptive — item actions when an item is aimed at, shape actions when a drawn shape is, then always the board actions. Aiming inside an existing multi-selection **keeps** it (that is where the group actions live); empty space clears it. Right-click never starts a gesture: move, resize, rotate, marquee, pan, drawing and the crop box are all left-button only.
- **The right-click policy is app-wide** (`components/common/TextContextMenu.tsx`, mounted once per window in `App.tsx`): the WebView2 native menu is suppressed everywhere, and text fields — board notes, dialogs, settings — get an in-app Cut / Copy / Paste / Select all menu instead; a plain text selection outside a field gets Copy. Its listener runs in the **capture** phase, so a field being edited on the board opens the edit menu, not the board menu; surfaces carrying their own `<ContextMenu>` (board, home cards, error badge) are left alone. Inside a dialog the menu is portalled **into** the dialog content, otherwise its clicks would read as an outside press. The home screen, which has no toolbar, carries its own menu (new project, open project, storage folder, settings).
- **Tooltips**: every icon button goes through the custom `Tooltip` wrapper; native `title=` is never used. Colour pickers are wrapped in a `TooltipTrigger render={<span/>}` so the picker's own popover trigger stays inside. A button that mirrors a shortcut takes its `action` and **shows the key in its tooltip**, read from `prefs.shortcutKeys`, so a rebind shows up without opening Settings.
- **The board background is a LAYER, not the container's colour**: its opacity (`background.opacity`, Appearance tab) reaches the flat colour and the dot grid, never the media on top. Below 1, `<html>` takes `nr-see-through`, dropping the page background and the shells that painted their own (detached window, pinned board), so what shows through is the window — hence `transparent: true` on both. The SCOPE is a setting: the interface (title bar, toolbars, floating panels, all tagged `nr-chrome`) keeps an opaque surface by default, since a translucent title bar over a busy desktop stops being readable, while the placement frame follows the background.
- **Alt + wheel sets opacity, never zoom**: over a medium it changes that item's `opacity`, over empty board the whole content layer (`prefs.contentOpacity`, one `opacity` on the transformed layer, so a per-item value multiplies with it). Both are floored at 10 % — a board you can no longer find is a board lost — and each turn of the wheel says the reading in the notice bar, so a half-invisible board never reads as a bug. The background, the content and the interface are three separate opacities: you look THROUGH the references while drawing under them.
- **Transparent to the mouse** (`boardMouseThrough.ts`): the window ignores clicks, wheel and hover (`setIgnoreCursorEvents`), which reach the application underneath. The way out cannot be a click — it no longer arrives — so it is the **return of focus** (Alt+Tab, taskbar), explained once before the mode engages. It also forces always-on-top while it lasts (and restores the previous state on exit): a click-through window sitting behind the application underneath would vanish on the first click. Never persisted, and unmounting the board restores the mouse.
- **An import that is still loading follows its placeholder**: the arriving media lands where the loading square *is*, not where the link was pasted. A dropped file re-centres on its live position; everything a link added is shifted by the placeholder's travel, so a carousel keeps its row.
- Media elements are `display:block` (`<video>`, `<img>`, YouTube iframe) to avoid the thin horizontal line from inline baseline gaps during playback.

## Folders (`boardFolders.ts` + `FolderBreadcrumb.tsx`)

- A frame with `folder: true` is folded into a card; its content lives one level down. The store keeps only the level on screen in `items` and parks every other level in `stash`; an item's `parent` names its folder and is written when the item is parked.
- Everything that saves, shares or diffs reads the **whole scene** (`sceneItems(items, stash, currentFolder)`), never `items` alone, or the other levels would be lost.
- Changing level clears the selection and the undo history; folding, unfolding and dropping an item on a card are one undo entry each (`stash` is restored with the snapshot).
- Collaboration: `setFolder` and `setParent` ops, each under its own key, so an older build shows the board flat. A shared board has one drawing layer, at the top level.

## PDF cards (`boardPdf.ts` + `PdfViewer.tsx`)

A PDF is an `image` item showing page 1 (other document types: see Documents below) (rendered once with pdf.js at ~1024 px, saved as a PNG asset), plus `docFile: { ref, name, type: "pdf", pages }` pointing at the document. The collaboration kind enum stays closed: peers see the thumbnail, never the file. Double-click (or the context menu entry) makes the card live: `PdfViewer` (lazy) opens the document, stacks every page and renders only those near the scroller's visible area; leaving live mode unmounts it and destroys the pdf.js document. `docFile.ref` is a media ref like any other: kept by `refsOf`, adopted into the project folder on save, bundled as a blob in a shared `.netsu`.

## Documents (`boardDocs.ts` + `boardDocRender.ts` + `DocViewer.tsx`)

Same model as a PDF card for every document type: an `image` item (the thumbnail) plus `docFile: { ref, name, type, pages?, view? }`, `type` being `"pdf" | "docx" | "text" | "markdown" | "csv" | "file"`. `docTypeOf` maps the extension (images and videos always win and import as media): `.docx` through mammoth, `.txt .log .json .srt .ass …` as preformatted text, `.md` through our small Markdown renderer (HTML escaped first; links only http, https, mailto; images never load), `.csv .tsv` through our RFC 4180 parser into a table, everything else (`.xlsx .pptx .doc .odt .zip .rtf …`) a `"file"` card (extension badge, name, size). Thumbnails are 800x1000 on white paper (html-to-image, canvas text as a fallback) or 800x600 for a `"file"`; a new card has a long side of `max(mediaMaxSize, 560)` (a `"file"` card keeps `mediaMaxSize`). A file without disk path is first saved as an asset under its own extension (`DOC_SAVE_EXTS`, mirrored by `EXT_OK` in `core/reference.js`; unknown extensions are kept as `.bin`). Every converted HTML goes through `sanitizeHtml` (allowlist, no script, handler, style, external load). `docFile.ref` is type-agnostic in `refsOf`, `sceneRefs`, the project adoption and the `.netsu` blob (its extension comes from the file). Double-click: `DocViewer` (scrollable paper, zoom, "open in system app"); a `"file"` card opens in the system app. The Add menu entry "Document" accepts all of these.

PDF extras: the live viewer fits the page width to the card and renders at screen density x board zoom (capped, 4096 px per canvas side). `docFile.view` (`"scroll"` or `"pages"`) is the reading mode of the card: `"pages"` is a carousel (one page, prev/next, Left/Right keys captured while live). "Extract pages" (context menu and live toolbar) renders up to 100 pages at 2048 px to PNG assets, then adds one `sequence` item or a grid of images to the right of the card, in a single undo step (`boardDocExtract.ts`).

## Text modes (`blockModel.ts` + `TextBlock.tsx` + `blockActions.ts`)

One `text` item, three modes, switched in place from the inspector (Text | Block | Sheet) or the right-click menu ("Display as…"). `noteMode(item)` is the single decision:

- **Text**: no `doc`, no `noteStyle`. Plain note edited in place (`TextNote`), fonts, colours, background.
- **Block**: `noteStyle: "postit"` and Markdown source in `text`. `"postit"` is only the on-wire value the Rust document already validates (`setNoteStyle` accepts `card` and `postit`); the product never says post-it. `text` syncs through the text CRDT, so a build without blocks still shows readable text. `TextBlock` renders it with `renderMarkdown(src, { tasks: "interactive" })` (nested lists by indentation, tasks, pipe tables, code, quotes; HTML escaped first, links only http, https, mailto and opened with `nr.openExternal`). Task checkboxes tick in view mode (`toggleTaskLine` rewrites the source line). Double-click edits the raw Markdown in the same box (Escape, Ctrl+Enter or a click outside leaves). A box too small for its content scrolls inside, and the wheel is the block's only while it can scroll.

  - **Entering the editor** does not rely on the browser's `dblclick` (retargeted by the pointer capture of the move gesture). `BoardItem` reads two taps from the pointer itself (`blockGesture.ts`: `isTap` + `registerTap`); the native `dblclick` stays as a second path. `usePointerTransform` keeps `dragging` as real state (a ref read at render left the grab cursor stuck after a click that never re-rendered), starts a move only after 3 screen px (a click or double-click jitter never commits or costs an undo step), ends on pointerup, pointercancel, `lostpointercapture`, window blur (commit) and Escape (cancel), closes a gesture still open before starting another, and is aborted when the item enters edit mode. A press on a link or a checkbox inside a block does not start a move (it would capture the pointer and swallow the click).
  - **Writing** (`blockEditing.ts`, pure and tested; `blockEditorDom.ts` applies it to the textarea): Enter continues `-`, `*`, `1.` and `- [ ]` lists (empty item ends the list, or goes one level out) and numbered lists are renumbered after every edit; Tab / Shift+Tab indent lines (selection too); Ctrl+B bold, Ctrl+I italic, Ctrl+Shift+X strike, Ctrl+E code, Ctrl+K link (selects `url`), Ctrl+1/2/3 headings, Ctrl+0 paragraph, Ctrl+Shift+7/8/9 numbered/bullet/task list, Alt+Up/Down move lines; typing `[] ` at line start gives `- [ ] `, `1) ` gives `1. `. `BlockEditBar` shows a slim formatting bar above the block while editing (constant screen size via `chromePx`, same transforms, tooltips with the shortcut) and a `/` menu at line start (headings, lists, task, quote, code block, divider, table; filtered as you type).
  - **Look** (`BlockControls`): font = `fontFamily`, size = `fontSize` (S/M/L presets 13/15/18 or any value), text colour = `color`, surface = `highlight` (a block has no text highlight, so the synced field is reused; unset = theme surface), accent bar = `bg` (palette or custom). Border on/off, corner radius S/M/L and padding S/M/L have no field in the shared document: they live in the local `blockLook` (not synced, lost when a collaborator's projection rebuilds the item, until a Rust field exists).
- **Sheet**: `doc` present, see below.

Switching (`switchNoteMode`, lazy BlockNote serialisers): Text and Block keep `text`; to Sheet, Markdown becomes blocks (`markdownToBlocks`); from Sheet, blocks become Markdown (Block) or plain text (Text). A sheet with content Markdown cannot hold (images, embeds, callouts…; `sheetIsRich`) refuses the switch with a notice and stays a sheet: nothing is dropped. Legacy post-its (`noteStyle: "postit"` + a `doc` of plain lines) display as blocks from `legacyMarkdown(doc)` and migrate on first edit or first tick (`text` written, `doc` dropped); a legacy post-it whose `doc` holds more than plain lines stays a sheet.

## Note sheets (`NoteCard.tsx` + `NoteOverlay.tsx` + `note/`)

- A sheet is a `text` item carrying `doc` (BlockNote JSON); `text` mirrors its plain text. The card renders a preview from the JSON; the editor (`note/NoteEditor.tsx`, BlockNote + Mantine, MPL-2.0) is lazy-loaded when a sheet opens and keeps its CSS in its own chunk.
- Edits reach the board debounced; one opening is one undo entry.
- Collaboration: `setDocument` writes the whole JSON (last writer wins per sheet, no character merge yet).

## `.netsu` container

`core/netsu/`, façade `core/netsu.js`. The share and project format is a **SQLite container**, no longer a ZIP.

- A file written in one shot cannot be the source of edits. Here items are **one row each** (`board_items`) and media bytes are **content-addressed and chunked** (`blobs`/`blob_chunks`, 8 MiB) — `node:sqlite` exposes no incremental blob API, so a multi-gigabyte medium never passes through memory whole.
- `db.js`: `page_size=8192` **before** the first write, WAL, `synchronous=NORMAL`, `rev` incremented per transaction, `seal(dest)` = checkpoint + `VACUUM INTO` (**never** `VACUUM` on the open database). Export writes a `.part` **inside the target folder** then renames (atomic on the same volume), so a half-written `.netsu` never exists.
- **The type is decided by the first bytes** (`sniff`: `SQLite format 3\0` vs `PK\x03\x04`), not by the extension: v1 ZIP archives already sent out stay importable (read-only legacy path).
- **"Save as" makes the `.netsu` the WORKING DOCUMENT** (`core/netsu/{session,project,sidecar,recents}.js`, tested). Sharing and saving are different operations and do not share code: sharing builds a **self-contained** file in one shot with re-encoded media; a project rewrites the **same** file a hundred times. Four rules:
  1. **The file stays OPEN** (session registry keyed on the resolved lowercase path — two spellings of the same file on Windows would open two databases on one file). Two caches live there for the same reason: content identity per path (otherwise every save re-reads the first megabytes of every rush) and last JSON written per item.
  2. **Incremental writes, compared on the item's JSON**: a thousand-item board with one moved item writes one `UPDATE`, and a save with no change writes **zero** rows (locked by test). That is the reason for the row-per-item schema.
  3. **No re-encoding**: a project only **references** rushes. The share path re-encodes per medium, which would mean tens of seconds per save.
  4. **Companion folder `my-project.medias/`**: whatever has no home of its own on disk (a pasted image, a medium fetched from a link) used to live in the **global** asset store shared by every board, so a project saved elsewhere left its media behind and clearing the store broke unrelated projects. The token path is **relative** to the `.netsu`, the only form that survives a move, and the pair moves together. The folder is **browsable**, so it is sorted: `images/`, `videos/`, one folder per image sequence under `sequences/`, `other/` as a fallback, and each file is named after its board item with a 12-hex content suffix (`aurora-2f4a70a71de8.jpg`) — that suffix is what keeps deduplication free. A save **never moves an already-sorted medium**, even when its item was renamed: a Ctrl+S must not churn the folder. A project written in the older flat layout is sorted on its next save by **renaming**, never by copying bytes. A media adopted from another project's companion folder (that is, "Save as") moves into the new one, so the copy does not stay tied to the original. A `..` in a received token cannot escape the folder, and orphan cleanup — which also prunes emptied sequence folders — is **suspended when a save empties the document at once** — that is almost always a board that has not loaded yet, and bytes do not come back.
- **Nothing a save deletes can still be needed.** Cleanup is the only step that destroys bytes, so three things feed its keep list. The **media held before an upscale** (`prevMedia`) is tokenised and adopted like any other project medium — otherwise the "undo upscale" button pointed at a file the same save had just erased. The board sends `retain`, the durable locators its **undo history** still holds: autosave fires 500 ms after a deletion, and without that list Ctrl+Z brought the item back without its pixels. Finally **saves are serialised per file** (`queued` in `core/netsu.js`): a save that copies a rush outlives the next autosave tick, and two concurrent passes would let the older one's cleanup erase what the newer just adopted.
- **A project does not pay twice for the same medium.** Blobs are cleaned like companion files: bytes no room references leave, and `PRAGMA auto_vacuum = INCREMENTAL` (set at creation) returns the freed pages. Opening a shared file as a project copies its media into the companion folder, so keeping the embedded originals would double the file for good. Copying and hashing large media run **asynchronously**, one chunk per transaction (`putFileAsync`, `adoptAsync`): the core is single-threaded, and a synchronous multi-gigabyte copy froze previews, the media server and every other module for the duration. Sharing reports its progress item by item over `netsu:progress`.
- **A shared file describes media, never machines.** Export writes `media.path` empty: an absolute path means nothing on the recipient's disk and publishes the sender's session name and disk layout, while relocation works on name + size + head fingerprint. `prevMedia` is reduced to its **origin link** if it has one and dropped otherwise — its bytes live with the sender, embedding them would double the weight for a version nobody looks at. Missing media relocate **in bulk** (`netsu:relocateFrom`): one folder, every medium recognised by name and size, and homonyms of equal size are never guessed.
- A board bound to a file **leaves** the internal library (`sceneId: null`): two copies of one board would diverge. After "Save as" succeeds, the file recent records the converted internal scene id, then removes that scene; the id remains a de-duplication guard if cleanup must be retried. NetsuBoard renders session, file projects, and unconverted scenes in one **Recent** grid. The recents registry otherwise stores file addresses, filters missing files **on read** and never rewrites, so a project on an unplugged drive is not forgotten forever. A v1 ZIP archive opens **read-only** rather than being refused; "Save as" converts it.
- **The global asset store is swept at boot** (`refStore.sweepAssets`, `NR_HOME/reference/assets`). It receives everything the app makes for a board — pasted images, fetched media, extracted frames, **upscale outputs**, hundreds of megabytes per shot — and nothing ever left it. A file goes only if no library scene references it (item refs, sequence frames, `prevMedia`, `localMedia`) **and** it is older than the 14-day grace period. It runs at startup and only there, because a board opened from a `.netsu` still points at that store in memory. Board upscales also go through `core/upscaleLedger.js` now: same source, same bounds, same settings returns the file already produced instead of paying for the GPU again.
- **Media embed levels** (`core/netsu/levels.js`, pure, tested): `link` (poster only) · **`preview` (default, the played range re-encoded)** · `margin` (widened range so bounds stay adjustable without the original) · `full`. Quality and margin are settings. **Do not produce embedded media through `proxySegment`**: it caps duration at 4s for looping previews — `core/netsu/embed.js` reuses the encoding building blocks without that cap or the playback queue. `netsu:weigh` estimates the weight of all four levels without encoding anything. An abnormally long range is **reported, never silently trimmed**.
- **The notebook is a `.netsu` document too** (`core/netsu/notebookDoc.js` + a router in `core/notebook.js`, tested). SQLite was chosen for the **access pattern**, not the file size: the notebook saves **as you type** (700 ms debounce) and one keystroke touches **one** page, whereas the ZIP re-serialised the whole page index and recompressed it at every pause, and had to be fully decompressed to open a single page or search a word. `sqliteBackend` takes a **handle** instead of a path, so the same tables and queries live either in `NR_HOME` or in a container. `createNotebookStore` became a **router**: channels do not all carry the target notebook, so routing uses the most precise id available and otherwise asks each store which one owns the object — a primary-key `SELECT`, never a scan. Files come **before** `NR_HOME`: after "Save as", the file is the truth. Three points hold: the notebook **keeps its id** when moving (otherwise its pages, mentions and subpages point at a vanished notebook), the trash follows, and the original copy is removed from `NR_HOME` only **after** verifying the number of pages written (a full disk must not leave the user with no notebook at all). Media go to the companion folder — **flat, at its root**, since a notebook token carries a file name and no path — and their URLs are stored as **tokens** (`core/netsu/mediaTokens.js`): a block URL carries an absolute path and a port, neither of which survives moving the project or restarting the core on another port. The renderer supplies its URL template on open — only it knows its base and token.



> The notebook document type is part of the `.netsu` router, but **the notebook itself is not a NetsuBoard surface**: `src/components/notebook/` is inherited from NetsuRush and nothing in `App.tsx` reaches it.

## Turbo upscale on a board item (`boardUpscale.ts` + `UpscaleItemDialog.tsx`)

Upscaling an item is a board action, not a module: pick a shader and a factor, the core runs one ffmpeg `libplacebo` job, and the result replaces the item's media. The engine rules — shader ids, ArtCNN suffixes, the `master`-build ban — are invariants and live in [`invariants.md`](invariants.md#turbo-upscaling--shaders-only).

- `useBoardUpChoices.ts` narrows the shader list to what the machine can actually run; a GPU without a working Vulkan/`libplacebo` path offers nothing rather than failing mid-job.
- Three shapes, one engine: still image → PNG, **animated GIF → GIF** (`runShaderGif`, all frames), video → HEVC mp4. The core picks by extension, so a Giphy item upscales like any other picture.
- In dev the shaders live in `vendor/shaders` (gitignored, `scripts/fetch-shaders.ps1`). Without them **every** job fails, video included — the directory is also the ffmpeg working directory.
- **A still frame is read without `-ss`.** An input seek to 0 on the image2 demuxer eats the only frame: ffmpeg writes nothing and still exits 0, so the board ended up pointing at a file that was never created. `writeFrame` also refuses an empty output rather than reporting success.
- **`libplacebo` drops alpha** whatever `format=` asks for. A transparent source is split (`alphaGraph`): colour through the shader, alpha scaled beside it with lanczos, `alphamerge` at the end — and for a GIF, a reserved palette entry (`reserve_transparent`, `alpha_threshold`).
- There is **no AI engine and no fallback to one**. `core/upscaleArgs.js`, `core/upscaleLedger.js` and the `netsulab-*` tests still describe NetsuRush's Python upscaler; they are inherited, not a second engine to reach for.

## Loop export of a board clip (`boardLoopExport.ts` + `ExportLoopDialog.tsx`)

A video item can be written as an **animated image that loops on its own** wherever an image is shown — a chat message, a web page — which a video file does not. The export follows what the board shows of the clip (loop bounds, crop, mirror), goes to a path the user picks, and leaves the item untouched.

- **Animated WebP is the default, GIF is the compatibility format.** WebP keeps 24-bit colour at a fraction of the weight; a GIF is capped at 256 colours per frame by the format, and no recipe makes it match WebP.
- **A GIF gets a palette per frame by default** (`palettegen=stats_mode=single` + `paletteuse=new=1`): a picture with many hues at once — a whole board above all — keeps far more of them than under one palette for the clip. The price is that every frame is written whole, so a picture that barely moves weighs several times more; "Better colors" unticked goes back to one palette weighted towards what moves, with only the changed area of each frame rewritten (`stats_mode=diff`, `diff_mode=rectangle`). **The two never combine**: a changed-area frame painted with its own palette corrupts the pixels it leaves untouched.
- **A GIF is encoded at a cadence it can store** (`playableFps`): delays are whole hundredths of a second, so 24 fps would be written as 4 cs and play at 25, 30 as 3 cs and play at 33. Encoding at the played rate keeps the speed and the loop length exact.
- `core/loopExport.js` runs **one ffmpeg pass** (`libwebp_anim`, or the `gif` muxer) into `<out>.part`, renamed on success: a cancelled or failed export never leaves a truncated file at the chosen path. One export at a time; closing the dialog cancels it.
- **Capped at 60 s** (`MAX_LOOP_SEC`, checked on both sides): an animated image has no seeking and is decoded whole by whatever displays it. Cadence is capped at 60 fps for WebP and 50 for GIF, whose delays are stored in hundredths of a second.
- **Lossless is WebP only** (`-lossless 1` on `bgra` frames): exact against the decoded picture and several times heavier, so it is an option, not the default. GIF has no such mode.
- **The weight shown before exporting is measured, not computed** (`estimateLoop`): the core encodes one second from the middle of the range with the chosen settings and scales it to the full length. No formula predicts either format — both depend on how much the picture moves. A newer request replaces the one in flight, an export stops it, and only a file already on disk is measured: opening the dialog never downloads a remote medium.
- Width is a ceiling, never an enlargement. Both encoders ship in the provisioned ffmpeg runtime, so the feature adds no dependency.

## Loop export of the whole board (`boardLoopRender.ts` + `ExportImageDialog.tsx`)

"Export board" also writes the board as an animated WebP or GIF: whatever moves on it plays, everything else is still.

- **The board is composed again, not captured.** A playing `<video>` cannot be painted into a canvas frame by frame at a useful speed, so the renderer cuts the z order at each video (`loopRuns`): what lies between two videos is painted once as a full-size transparent PNG layer by `renderBoardCanvas` (`paint` restricts what is drawn without changing the framing), and each video travels as a clip with its place, crop, mirror, rotation and opacity. `boardLoopArgs` stacks layers and clips with `overlay` in one ffmpeg pass.
- **Everything that moves is a clip** (`loopSourceKind`): a video or GIF on disk is read as it is; a YouTube item is read through the core's own relay (`/ytstream`, the only URL `clipSource` accepts), nothing downloaded; an image sequence travels as its frame list (concat demuxer); a remote medium or an embed card is brought to disk when the export starts — the only step that can take long, and the dialog says so. What cannot be made readable (a shared-board medium, an animated WebP, which ffmpeg does not decode) is painted still with the rest, never dropped.
- **Each clip loops over its own range for the length of the export**, which is the longest loop on the board unless the user types another, capped at 60 s. A looped clip is buffered at its placed size, before the RGBA conversion — that is what keeps a board of many clips in memory.
- **Loops of different lengths are made to wrap together** (`loopSpeed`, on by default): each clip is bent to play a whole number of times in the export, so the file loops on a loop point of every clip instead of cutting most of them mid-way. The bend is capped at 12 %; past it the clip keeps its speed and takes the cut, since a visibly retimed clip is worse.
- A clip **fills its item as the board shows it** (cover), except the video of an embed card, which fits inside the card.
- **The cut is inside the filter graph** (`trim=duration`), never an output `-t`: still layers and looped clips are endless inputs, and `palettegen` reads its whole input before emitting anything.
- A transparent background survives in WebP; GIF always gets the board colour.

## Links

Obsidian-Canvas-style links between board items. A link is **not** a separate model: it is an
anchored `arrow`/`line` `DrawShape` with both `a1` and `a2` set, so persistence, undo and
collaboration already handle it. Everything lives in `src/components/reference/links/`:

| File | Role |
|---|---|
| `model.ts` | Pure: anchors, side choice, routing, heads, hit-testing, label layout and label style encoding, palette, width, identity helpers. |
| `junction.ts` | Pure: junction encoding and checks (cycles, depth), root items of a flow, item edges through junctions, downstream/upstream, collapse, cascade delete and re-root, detach, path sampling. |
| `resolve.ts` | Pure: geometry of every link, junctions included, parents first, cached by a key that includes the parent's. Shared by the layer and the export. |
| `graph.ts` | Pure: neighbours and connected groups, chain/star pairs, insert into a link, link copies for duplicated items, the Organise layouts. |
| `gestureModel.ts` | Pure: gesture kinds, link targets of a dragged end, what a released gesture writes. |
| `useLinkScene.ts` | The one geometry selector: store items merged with live gesture geometry, resolved through `resolve.ts`. |
| `LinkLayer.tsx` | Single owner of link rendering, hit areas, junction dots, collapsed subtrees, focus, hover highlight, selection UI, insert hint, pick mode hint. |
| `LinkHandles.tsx` | Connect handles of one item, end handles of the selected link, branch dot, collapse badge, target hint. |
| `LinkLabel.tsx` | Label pill (styled) and inline editor. |
| `LinkEditorMenu.tsx`, `LinkStyleControls.tsx`, `linkToolbarParts.tsx` | Floating toolbar of the selected link(s) and its style panels. |
| `LinkDropMenu.tsx` | Popover after a drop on empty space: note sheet, text, block. |
| `LinkMenuItems.tsx` | Link entries of the right-click menu (item, link, multi-selection). |
| `LinkSettings.tsx` | Settings > Links: defaults of new links, focus toggle. |
| `linkActions.ts` | Store-level commands (link selection, select linked / downstream / upstream, unlink, delete with re-root, detach a branch, reverse, collapse, organise, insert, Tab cycle, multi-edit). |
| `useLinkGesture.ts` | Drag of a link end (new link, re-attach, fork, branch, merge, junction slide), Escape cancels. |
| `useLinkShortcutsOnBoard.ts` | Ctrl/Cmd-drag an item to link it; "Link to..." pick mode. |
| `useInsertOnDrop.ts` | Drop of a moved item onto a link. |
| `usePointerNear.ts` | Item under / near the pointer (handles, hover highlight). |
| `linkUi.ts` | Transient UI state (label being edited, hovered link, pick mode, Tab pivot, collapsed subtrees). |

`DrawLayer` skips links entirely (no drawing, no hit target, no handles, no inspector).

- **Anchors**: an end is AUTO when its fraction is exactly the item centre (`fx = fy = 0.5`): it
  re-picks the side facing the other end every time either item moves (`sideToward`, split along
  the box diagonals). The sentinel stays inside the 0..1 range the collaboration document
  validates. Any other fraction is FIXED: a side midpoint pins that side; older links and
  hand-drawn arrows keep their exact point and leave along their closest side. A link is never
  re-anchored from its points (`reanchorShape` returns it unchanged).
- **Create**: handles (four tiny low-contrast dots, outside each side) appear only for one item —
  the one whose edge the pointer is near, else the single selected item — and never while
  navigating, during a gesture, in draw mode, for a viewer, or below `chromeVisible`. Dragging one
  previews the link; over an item it targets that item (auto) or, near a side, pins that side.
  Release on an item writes one history entry; on empty space a popover creates a note sheet or a
  text block there and links it (one undo entry).
  The popover offers a note sheet, a text note (Settings text defaults) or a Markdown block. Links
  drawn from scratch take the Settings > Links defaults (route, heads, line, colour, width, label
  font and size).
- **Re-attach / fork**: the selected link shows its two end handles; drag one to another item or
  side, onto another link (it becomes a junction there), or to empty space to create an item there.
  **Alt**-drag an end keeps the link and draws a copy of it (same style) with that end moved.
- **Junctions** (node-editor style): a link END can sit on ANOTHER LINK. Encoded with the existing
  anchor, no new field: `{ id: <parent link id>, fx: t, fy: 0.5 }`, `t` = arc-length fraction along
  the parent's path, clamped 0.05..0.95. Item ids and shape ids never collide, so the lookup tells an
  item end from a junction. Junctions nest (a branch of a branch) up to `JUNCTION_MAX_DEPTH`; a link
  never hangs from itself or its descendants (`canAttach`), and a cycle or a missing parent is
  simply not drawn (a branch that arrives before its parent through collaboration shows up when the
  parent does). The junction point is recomputed from the parent's LIVE path, so it follows items in
  real time. A branch leaves its parent along the parent's tangent, oriented toward its other end:
  one wire splitting in two (fork) or two joining (merge). A small dot marks the junction (link
  colour, low contrast, clearer on hover/selection); a junction end never carries an arrowhead.
- **Branch** (fork): a hovered or selected link shows a grab dot that follows the pointer along it
  (at the midpoint, beside the label, before the pointer moves on it); **Alt**-drag anywhere on a
  link does the same. Dragging out previews the branch leaving tangentially; release on an item
  creates the branch link (same style as the parent, no label), on empty space opens the drop
  popover. One undo entry.
- **Merge** (fan-in): any dragged end (a new link from a handle, a re-attached or forked end) that is
  away from every item but within reach of a link attaches to it at the pointer's `t`; the target
  link lights up during the drag.
- **Editing junctions**: drag a junction dot along its parent to slide it (clamped), off it onto an
  item to make it a normal end, or onto another link. A press without a drag selects the branch.
  Right-click a junction (or a branch): "Detach branch" moves the end to the parent's nearer item
  (source before the middle, target after; the branch goes if neither is possible), "Delete
  branch". Deleting a link re-roots its branches (a fork on the parent's source item, a merge on its
  target item, keeping their style; removed when impossible, and so on down) in the same undo entry
  (`removeShapes`); deleting an item does the same for its links (`pruneLinks`). Reversing a link
  mirrors its branches' `t`; inserting an item into a link moves the branches of the second half
  onto the new second link.
- **Node logic**: a link has a source and a target. A branch counts as an edge from the flow's
  source item to its target item (`itemEdges`: a fork from the parent's source, a merge into the
  parent's target), which is what focus, hover highlight, Tab cycling, select linked / group,
  Organise and the directed commands read. "Select downstream" (`Alt+D`) and "Select upstream"
  (`Alt+U`) follow the direction through junctions. "Move with downstream items" (item menu or
  Settings > Links, `linkMoveSubtree`) makes a moved item carry its whole subtree, live and in the
  same undo entry. Collapse / expand (`Alt+C`, item menu, or the small badge at the bottom-right of
  the item under the pointer, always shown on a collapsed item with the hidden count) hides the
  downstream items (CSS `visibility`) and their links; view only, local to the window, never saved
  or shared, ignored by the export.
- **Reroute points**: not implemented. The manual control point `cp` is stored in world
  coordinates, so a bend would not follow the items, and double-click already edits the label.
- **Fast linking**: `L` links the selected items in selection order as a chain, `Shift+L` from the
  first selected item to every other one (star); existing links (either direction) are never
  duplicated. `Ctrl+L` / "Link to..." enters a pick mode: the next item clicked is linked from the
  selection, a click elsewhere or Escape cancels. Ctrl/Cmd-drag an item draws a link from it instead
  of moving it (a Ctrl/Cmd-click without moving toggles it in the selection). `Alt+L` selects the
  linked items, `Ctrl+Shift+L` the whole connected group; "Remove links" is unbound by default.
  Every shortcut is in the rebindable table (`SHORTCUT_DEFS`), so it shows in Settings.
- **Insert into a link**: a lone item dragged with its centre over a link lights that link; released
  there, A>B becomes A>X>B (the first half keeps id, style and label; one undo with the move). To
  see the item move, `usePointerTransform` publishes live geometry for a lone item on any board that
  has links.
- **Organise** (item menu, link menu, `Alt+O` replaying the last mode): tree left to right, tree
  top to bottom, or mind map (rings around the root, wedges in proportion to leaves), computed by
  `organiseLayout` over the undirected item edges (junctions included) from the root (the item, or a
  link's source). The root
  stays put, sizes are kept, siblings keep their current order, one undo entry. The board has no
  lock/pin concept on items, so every item of the group moves.
- **Copies keep links**: Ctrl+D on several items and the internal copy/paste carry the links whose
  two ends are in the copied set, re-anchored onto the copies, and the branches between them,
  hanging from the copied parents (`remapLinks`).
- **Routes**: `curved` (cubic leaving each side along its normal, default), `straight`, `elbow`
  (orthogonal, rounded corners). Heads none/end/both (filled arrowhead, path trimmed under it),
  solid/dashed. Colour: a palette of mid-tone colours readable on both themes, the last eight custom
  colours (kept in prefs, added when the colour panel closes), a full colour picker, and an opacity
  (`op`). Width: thin/normal/bold presets or any value from 0.5 to 12. The stored `w` is a width in
  screen pixels (clamped); the drawn width is that times `chromePx(scale)`, like every piece of link
  chrome.
- **Label**: stored in `text`, a horizontal pill at the arc-length midpoint, two lines then an
  ellipsis (`labelLayout`); the path is masked under it. Hidden below `chromeVisible`. Double-click
  the link or the label to edit; an empty label removes it. Its style (font, size S/M/L or custom,
  text colour, pill background, transparent allowed, bold, italic) is stored in the link's `fill`
  as `nbl1|bg|color|size|flags|font` (`formatLabelStyle` / `parseLabelStyle`), kept within the
  document's 128 characters by cutting the font name. `fill` is a field every vector shape already
  syncs and links did not use, so the label style syncs with no new collaboration field; the export
  strips it so it never paints the path.
- **Selection**: click the link (wide transparent hit path; hover lights a halo in CSS),
  Shift+click to add links. The selection gets a compact toolbar under the last link's midpoint:
  route, heads, line, width, colour, label style, label (one link only), reverse, delete; with
  several links every change applies to all of them. Delete/Backspace and the right-click menu
  (`BoardMenu.tsx`) work as for strokes. `Tab` / `Shift+Tab` steps through the links of the
  selected item (then keeps that item as the pivot). Hovering an item lights its links faintly.
- **Real time**: geometry is read through `useLinkScene`, which merges `boardLive` geometry
  (published by `usePointerTransform` for the moving item, the rest of a multi-selection, the
  content a frame carries — culled items included — and a frame hugging its content), coalesced to
  one update per frame. Undo/redo and collaborator edits arrive through the store.
- **Focus**: with one item selected (setting "Highlight links of the selected item"), its links stay
  lit, the others dim, and the reached items are outlined.
- **Levels**: a link is drawn only when both ends resolve on the level on screen (an item there, or a
  parent link drawn there); links into a folded folder or towards a deleted item are skipped.
  Deleting an item removes its links in the same history entry and repairs their branches
  (`pruneLinks`).
- **Export** (`boardRender.ts`) draws links with the same resolver (junctions included), at a chrome
  factor of 1.
- **Performance**: one SVG for every link inside a `data-board-pan` layer (pan never re-renders
  it), links resolved in topological order (parents first) and memoised per link by a key of its
  own geometry and its parent's key, viewport culling with one viewport of margin. The branch dot
  follows the pointer imperatively (no React render per move).
